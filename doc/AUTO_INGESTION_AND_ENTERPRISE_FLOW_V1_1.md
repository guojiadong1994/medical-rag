# Medical RAG V1.1：自动知识入库与企业流程对齐

## 1. 为什么要从“人工脚本”升级

前面的开发阶段故意把流程拆开：解析、清洗、分块、向量化、检索、评测分别运行，目的是看清每个环节并方便排错。

产品阶段不能要求管理员每增加一份医学资料就手动执行多条命令。真正面向业务的知识库通常把这些步骤组织成一条自动的“知识入库流水线”。

当前 V1.1 将网页上传后的处理改成：

```text
上传 PDF
→ 创建知识文档记录
→ 后台任务开始
→ PDF 解析与清洗
→ 章节/段落/表格分块
→ BGE-M3 生成语义向量
→ 标记为可检索
→ 重载当前问答检索器
```

管理员只负责“上传资料”和“查看状态”，不再手工运行 parse/chunk/embed 命令。

## 2. 当前本地产品与真实生产系统的对应关系

| 能力 | V1.1 本地产品 | 企业生产环境常见做法 |
|---|---|---|
| 原始文件存储 | `data/knowledge/inbox` | 对象存储，例如 MinIO / S3 |
| 文档状态记录 | JSON 注册表 | PostgreSQL 等关系数据库 |
| 后台任务 | FastAPI 后台任务 + 独立 Python 子进程 | 独立任务队列与 Worker（工作进程） |
| 文档解析 | 项目现有 PDF 解析器 | 独立文档处理服务 |
| 文本分块 | 项目现有结构感知分块 | 统一分块服务和版本化策略 |
| Embedding（语义向量生成） | BGE-M3 | 独立向量化服务 / GPU 推理服务 |
| 检索索引 | 本地精确向量索引 | Milvus / Elasticsearch / OpenSearch 等 |
| 发布 | 文档处理完成后自动加入本地检索 | 增量写入 + 索引版本 + 灰度发布 |
| 监控 | 页面进度与错误信息 | 任务监控、告警、链路追踪、审计日志 |

`Worker（工作进程）`：专门在后台执行耗时任务的程序，不占用用户请求本身。

`增量写入`：新增或修改一份文档时，只处理发生变化的数据，而不是每次重新处理全部知识库。

`灰度发布`：新索引先在一部分流量或测试环境验证，再切换为正式索引，避免一次更新把线上检索弄坏。

## 3. 为什么 V1.1 使用独立子进程

向量模型在本地可能使用 MPS（苹果芯片 GPU 加速）。如果把文档向量化直接塞进网页请求线程，会有三个问题：

1. 上传接口会长时间卡住；
2. 大模型/向量模型内存与问答服务互相影响；
3. 某个底层模型崩溃可能直接拖垮网页服务。

所以 V1.1 的上传接口先快速返回，后台再启动独立 Python 子进程完成解析、分块和向量化。这和生产环境把耗时任务交给独立 Worker（工作进程）的思想一致，只是本地版没有强制引入 Redis、Kafka 等额外基础设施。

## 4. 为什么新增知识不再需要重新向量化旧文档

每份新文档都会生成自己的：

```text
chunks.json
embeddings.npy
embedding_manifest.json
```

旧文档的向量文件保持不变。

本地检索服务启动时，把所有“已索引”文档的知识片段和向量合并到内存中进行统一检索。因此：

```text
新增文档
→ 只解析/分块/向量化新文档
→ 旧文档不用重新生成向量
```

这已经具备“增量入库”的核心思想。

服务器版本如果切换到 Milvus（向量数据库），则应进一步改成：

```text
新文档向量
→ 直接 Upsert（新增或更新写入）到 Milvus
```

而不是每次重建整个向量集合。

## 5. 医疗知识库生产环境还应该增加的门槛

医疗场景不能简单做到“上传即上线”。更完整的正式流程应当是：

```text
数据接入
→ 自动解析
→ 质量检查
→ 元数据补全
→ 分块
→ 向量化
→ 离线检索验收
→ 人工审核（高风险资料）
→ 发布索引
→ 在线监控
→ 版本回滚
```

其中比较重要的是：

- 文档来源、发布日期、版本、适用人群等元数据必须保留；
- 指南更新时需要能识别旧版本并控制是否继续参与检索；
- 文档处理失败不能悄悄进入知识库；
- 新索引需要评测后再发布；
- 必须能够回滚到上一版索引；
- 每次知识更新需要有审计记录。

这些属于后续真正生产化时再补的能力，本地 V1.1 不强行引入复杂基础设施。

## 6. V1.1 前端交互调整

AI 健康助手新增：

- 用户发送问题后立刻出现处理中的助手气泡；
- 显示“正在分析问题 / 正在检索知识库 / 正在核对证据并组织回答”；
- 显示等待秒数；
- 清理不可见控制字符和异常替换字符；
- 对常见 Markdown（大模型常用排版格式）做安全渲染；
- 只把真正被答案引用的证据直接展示；
- 其他召回证据默认折叠，避免页面被无关卡片占满；
- 来源卡片增加实际证据摘要。

知识库管理页新增：

- 上传后自动开始处理；
- 实时轮询处理状态；
- 显示解析、分块、向量化、发布进度；
- 失败任务显示错误；
- 支持重新处理。

## 7. 面试可以怎么解释

可以概括为：

> 开发阶段我把 PDF 解析、Chunk（知识分块）、Embedding（语义向量生成）和索引分别执行，方便逐阶段验证。产品阶段我把它改造成异步知识入库流水线：管理员上传文档后立即返回，由后台任务独立完成解析、清洗、分块和向量化；每份文档保存独立制品，新增文档只计算新增向量；处理完成后刷新检索运行时。这个本地实现对应生产环境中的“对象存储 + 任务队列 + 工作进程 + 元数据数据库 + 向量数据库”的架构，后续可把本地后台任务替换成分布式任务队列，把本地精确向量检索替换成 Milvus 增量写入。
